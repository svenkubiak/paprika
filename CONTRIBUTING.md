# Contributing

Thank you for your interest in contributing to this project.

We welcome bug reports, documentation improvements, feature proposals, code contributions, tests, examples, and other improvements.

Because this project is distributed under a dual-licensing model, contributions must be made under terms that allow the project to continue to be offered under both its non-commercial and commercial licenses.

## Code of Conduct

Please be respectful and constructive when participating in the project.

Harassment, abusive behavior, discrimination, personal attacks, and intentionally disruptive behavior are not acceptable.

## Ways to Contribute

You can contribute by:

* reporting bugs;
* suggesting improvements;
* proposing features;
* improving documentation;
* submitting tests;
* submitting code changes;
* improving examples;
* reviewing pull requests; or
* helping other users in project discussions.

## Before Opening a Pull Request

Before starting significant work, consider opening an issue or discussion first.

This is especially recommended for:

* large features;
* architectural changes;
* breaking changes;
* changes to public APIs;
* changes to persistence formats;
* security-sensitive changes; or
* substantial refactoring.

This helps avoid duplicate work and makes it easier to align on scope and design.

## Contributor License Agreement

Before a contribution can be accepted, all external contributors must agree to the project's Contributor License Agreement ("CLA").

Contributions will not be merged unless the applicable CLA has been accepted.

The CLA ensures that the project can continue to distribute contributions under its dual-licensing model.

By signing the CLA, you do not necessarily transfer ownership of your contribution.

Instead, you grant the project the rights necessary to:

* use your contribution;
* modify your contribution;
* distribute your contribution;
* include your contribution in public releases;
* license your contribution under the project's non-commercial license;
* license your contribution under the project's Commercial License; and
* relicense your contribution as reasonably necessary for the continued development and distribution of the Software.

See `CLA.md` for the complete terms.

A contribution may be rejected if the required CLA has not been completed.

## Your Rights to Contribute

By submitting a contribution, you represent that:

* you created the contribution yourself or otherwise have the legal right to submit it;
* you have the authority to grant the rights required by this project;
* the contribution does not knowingly infringe third-party intellectual-property rights;
* the contribution does not contain confidential information that you are not authorized to disclose; and
* your contribution complies with any obligations you have to an employer, client, customer, or other third party.

If you are contributing as part of your employment, you are responsible for ensuring that you have the necessary authorization from your employer.

## Third-Party Code

Do not submit third-party code unless its license is compatible with the project's licensing model and its inclusion has been clearly disclosed.

If your contribution contains or depends on third-party code, please identify:

* the third-party component;
* its source;
* its license;
* any copyright notices; and
* any attribution or redistribution requirements.

Do not submit code copied from proprietary, confidential, or otherwise incompatible sources.

## Artificially Generated Contributions

Contributors are responsible for ensuring that any submitted code, documentation, tests, or other material can legally be contributed under the terms of this project.

If you use code-generation or AI-assisted tools, you remain responsible for reviewing the resulting contribution and ensuring that:

* you have the right to submit it;
* it does not knowingly reproduce incompatible third-party material;
* it meets the project's quality and security requirements; and
* it complies with this contribution policy.

## Pull Requests

Pull requests should:

* have a clear title;
* explain the purpose of the change;
* describe any significant design decisions;
* reference related issues where applicable;
* include tests where appropriate;
* update documentation where appropriate; and
* remain focused on a reasonably scoped change.

Large unrelated changes should generally be split into separate pull requests.

## Code Quality

Contributions should follow the existing project structure and coding conventions.

Where applicable, contributions should:

* pass automated tests;
* pass formatting and linting checks;
* avoid unnecessary dependencies;
* include appropriate tests;
* preserve backward compatibility where practical;
* handle errors appropriately; and
* avoid introducing avoidable security risks.

## Tests

Bug fixes should normally include a regression test where practical.

New features should include appropriate tests covering expected behavior and relevant edge cases.

Contributions that materially affect security, authentication, authorization, data isolation, or persistence may require additional testing.

## Documentation

User-facing changes should generally include corresponding documentation updates.

This may include:

* README changes;
* configuration documentation;
* API documentation;
* migration guidance;
* examples;
* release notes; or
* upgrade notes.

## Breaking Changes

Breaking changes should be clearly identified in the pull request.

Do not intentionally introduce breaking changes without discussing them with the maintainers first.

Where practical, breaking changes should include:

* migration instructions;
* compatibility notes;
* deprecation guidance; or
* an explanation of why the change is necessary.

## Security Issues

Do not report suspected security vulnerabilities through public issues or pull requests unless explicitly instructed to do so.

Please follow the process described in `SECURITY.md`.

## Licensing Changes

Changes to:

* `LICENSE`;
* `COMMERCIAL-LICENSE.md`;
* `LICENSING.md`;
* `CLA.md`;
* `NOTICE`; or
* other licensing or legal files

should not be submitted without prior discussion with the maintainers.

Pull requests that alter the project's licensing model may be rejected without review.

## Acceptance of Contributions

Submitting a contribution does not guarantee that it will be accepted.

Maintainers may:

* request changes;
* request additional tests;
* request documentation;
* delay review;
* close a contribution;
* reject a contribution; or
* modify an accepted contribution later.

Acceptance decisions are made at the maintainers' discretion.

## Contribution Attribution

Accepted contributions may be attributed to contributors through:

* Git history;
* release notes;
* acknowledgments;
* project documentation; or
* other appropriate project records.

Unless separately agreed, attribution does not create ownership, endorsement, employment, partnership, or support obligations.

## No Support or Compensation Obligation

Submitting a contribution does not create any obligation for the project or Licensor to:

* provide compensation;
* provide support;
* provide employment;
* provide consulting work;
* provide commercial licensing benefits; or
* include the contribution in any particular release.

Any such arrangement must be separately agreed in writing.

## Development Certificate and Sign-Off

If the project uses a Developer Certificate of Origin ("DCO") in addition to or instead of a CLA, contributors may be required to sign off commits using:

`Signed-off-by: Your Name <your-email@example.com>`

Any DCO requirements will be documented separately.

Unless explicitly announced otherwise, the CLA requirements described above take precedence for purposes of the project's dual-licensing model.
